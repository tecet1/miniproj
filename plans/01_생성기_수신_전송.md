# 계획 01. 이벤트 생성기와 Functions → Event Hubs 전송

## 목표

고정 시나리오에서 채널별 원본 이벤트를 생성하고, HTTP → Azure Functions → Event Hubs 경로로 전송해 도착 건수를 확인한다.

## 입력 / 산출물

- 입력: `01_contracts/contracts/` 의 `scenarios.json`, `skus.json`(기준 데이터), `scenarios.md`, `sku_spec.md`, 이벤트 명세
- 산출물
  - 생성기: `01_contracts/src/` (`timeutil`, `pricing`, `scenario_loader`, `scenario_validator`, `canonical`, `channel_a/b/c`, `faults`, `generate`, `expected`)
  - 픽스처: `01_contracts/data/fixtures/{A,B,C}/events.jsonl` (채널당 24건), `fixtures/expected/expected.json`
  - 수신·전송: `02_pipeline/ingestion/` (`function_app.py`, `eventhub_client.py`, `send_events.py`, `verify_arrival.py`, `requirements.txt`, `host.json`)
  - 테스트: `02_pipeline/tests/contracts`, `02_pipeline/tests/ingestion`
- 흐름도: `02_pipeline/ingestion/Ingestion_흐름도.pptx`

## 설계 결정

- 기준 데이터(SSOT)는 `scenarios.json`, `skus.json` 하나씩이며 `.md`는 규칙과 목적만 적는다.
- `events.jsonl` 한 줄은 `{"channel": "A", "payload": "<원본 본문 문자열>"}` 이다. 시각이 들어가지 않아 해시가 안정적이다.
- 송신기는 `payload`를 본문으로 `POST /api/events/{channel}` 하고, Function이 `received_at`을 찍어 봉투(`{channel, received_at, payload}`)를 만들어 Event Hubs에 보낸다.
- A·B·C 외 채널은 400, 성공은 202. Function은 payload를 해석하지 않는다.
- 파티션 키 없음(라운드로빈). 순서는 Silver가 이벤트 시각으로 처리한다.
- 인증: Function 키(`x-functions-key`, 환경 변수 `FUNCTION_KEY`), Event Hubs는 Managed Identity(Data Sender). Key Vault는 범위 밖.
- 송신 실패 시 재시도한다. 중복은 Silver에서 `channel + event_id`로 제거한다.
- 인프라: 허브 `commerce-events`(파티션 2개), 소비자 그룹 생성 완료. Databricks 읽기 자격은 Bronze 적재 계획에서 확인한다.

## 단계

0. 인프라 확인 (완료, 사용자 확인)
1. 기준 데이터와 명세 문서 정리 (`scenarios.json`, `skus.json`, md 중복 제거)
2. 생성기 모듈 구현: 모듈 하나씩 짝 테스트를 통과시킨다 (순서는 `01_contracts/src/README.md`)
3. `expected.py`로 `expected.json` 생성, `generate.py`로 `events.jsonl` 생성
4. Function 작성 (채널 검증 → 봉투 생성 → Event Hubs 전송)
5. 송신기 작성 (`events.jsonl` → HTTP POST, 재시도)
6. GitHub Actions로 배포 후 원격 실행
7. 도착 확인 스크립트로 소비자 그룹에서 건수·내용 대조

## 완료 조건

- 같은 입력으로 생성기를 반복 실행해도 `events.jsonl`이 동일하다 (해시 일치).
- 채널별 24건, 3채널 합계 72건. 중복(S19)은 같은 이벤트가 2건 포함된다.
- 채널별 원본 형식이 명세와 일치한다 (A: ISO 8601 UTC, B: epoch ms, C: KST 문자열).
- 3종 격리 변형(S21)이 채널마다 3건씩 포함된다 (합계 9건).
- `expected.json`이 `scenarios.md` 기준 손 계산값(총 판매금액 422,000 등)과 일치한다.
- 송신 후 Event Hubs에서 읽은 건수가 72건이고, 봉투의 payload가 원본과 같다.
- A·B·C 외 채널은 400을 반환하고 Event Hubs에 쓰이지 않는다.
- 저장소에 키·연결 문자열이 없다.

## 검증 방법

- 계약 테스트: `python -m unittest discover -s .\02_pipeline\tests\contracts -v`
- 생성: `python .\01_contracts\src\generate.py` 후 두 번 실행해 해시 비교
- 원격: 배포 후 송신기 실행, 도착 확인 스크립트가 출력한 건수를 `expected.json`과 비교
- 기대값은 구현 통과를 위해 수정하지 않는다.

## 보류 중인 명세 항목

- 환불 수량 필드명 (제안: A `refund_quantity`, B `refundQty`, C `rfd_qty`) — 승인 후 이벤트 명세에 반영
- 이벤트 명세를 `01_contracts/contracts/`로 옮길 때 refund_quantity, order_cancellations, received_at(Function 부여), 환불 금액 비례 규칙을 함께 갱신

## 범위 밖 (이 계획에서 하지 않음)
