# 계획 09. 병렬 작업 분배

## 목표
덤프 재설계 동안 파일이 겹치지 않는 작업을 Claude·GPT 세션 여러 개로 나눠 진행하고, 작업별 명세와 소유 경로, 통합 규칙을 한 곳에서 관리한다.

## 구조

- 작업 패키지(WP)마다 에이전트 파일 `plans/작업패키지/wp-*.md`에 요구사항 명세(목표, 입력·산출물, 완료 조건, 검증 방법, 상태, 소유 경로, 금지)를 적는다. GPT 세션은 이 파일을 일반 마크다운으로 읽는다. Claude Code에서 서브에이전트로 쓰려면 사용자가 `.claude/agents/`로 복사한다(원격 도구로는 `.claude`에 쓸 수 없다). 두 곳이 어긋나지 않게 `plans/작업패키지/`를 원본으로 한다.
- 세션 시작 프롬프트(공통): `AGENTS.md와 plans/작업패키지/wp-<이름>.md를 읽고, 그 파일의 범위 안에서만 작업하라. 변경안과 영향 범위를 먼저 제안하고 승인 전에는 수정하지 마라.`
- WP의 명세는 해당 에이전트 파일이 유일한 기준이다. 이 문서는 전체 배치만 다룬다.

## 공유 파일 규칙

- `plans/결정_로그.md`: 모든 세션이 쓴다. 맨 아래에 행 추가만 하고 기존 행은 고치지 않는다.
- `02_pipeline/tests/`: 층별 하위 폴더 단위로 소유한다. 다른 WP의 폴더는 고치지 않는다. `__init__.py` 추가가 필요하면 자기 폴더 안에서만 한다.
- `04_experiments/results/expected_dump.json`: WP-덤프만 수정한다. 다른 WP는 읽기만 한다.
- `01_contracts/`: 어떤 WP도 사용자 승인 없이 수정하지 않는다.

## 통합 규칙

- **브랜치를 분리한다(2026-10-15 사용자 결정).** 세션마다 별도 브랜치와 git worktree(작업 폴더)에서 작업하고, 사용자가 main에 병합한다. 브랜치 이름은 작업 키워드로 한다.

| WP | 브랜치 | worktree 폴더(제안) |
|---|---|---|
| WP-덤프 | `dump` | `..\miniproj-dump` |
| WP-Silver | `silver` | `..\miniproj-silver` |
| WP-Gold | `gold` | `..\miniproj-gold` |
| WP-Genie 벤치마크 | `genie-bench` | `..\miniproj-genie-bench` |
| WP-문서 | `docs` | `..\miniproj-docs` |

- **브랜치를 만들기 전에 계획 09, `plans/작업패키지/`, 결정 로그를 main에 커밋해 둔다.** 커밋 전에 worktree를 만들면 각 세션이 자기 명세 파일을 볼 수 없다.
- 생성 예(프로젝트 루트, PowerShell): `git worktree add ..\miniproj-dump -b dump`. 세션은 해당 폴더에서 시작한다. 의존성(`.venv`)은 git에 없으므로 폴더마다 준비가 필요할 수 있다.
- 결정 로그는 모든 브랜치가 맨 아래에 행을 추가하므로 병합 때 같은 위치에서 충돌한다. 충돌 시 양쪽 행을 모두 남긴다(날짜순).
- 커밋 메시지는 사용자가 정하고, 세션은 커밋·푸시를 하지 않는다(요청 시에만).
- WP-덤프가 `expected_dump.json`을 바꾸므로 WP-Silver·WP-Gold의 "덤프 기대값 일치"는 **병합 시점 main 기준으로 다시 돌린다**. 그 전 결과는 '잠정'으로 적는다.
- 병합 후 전체 테스트를 한 번 돌려 실패 3건(줄바꿈) 외에 늘어난 실패가 없는지 확인한다.
- 병합 순서 제안: WP-덤프 → (WP-Silver, WP-Gold, WP-Genie 1단계, WP-문서는 순서 무관) → 전체 테스트 → Databricks 재적재와 `check_*`(사용자).

## 진행상황 한눈에 보기

- 각 세션은 자기 WP 파일의 `## 상태` 절(한 줄)을 갱신한다. 작업 폴더의 파일이 현재 상태이고, 세션은 커밋하지 않으므로 커밋 이력이 아니라 worktree 폴더를 읽는다.
- 프로젝트 루트(PowerShell)에서 실행한다. worktree 폴더 이름이 `..\miniproj-<브랜치>`일 때 동작한다.

```powershell
foreach ($k in 'dump','silver','gold','genie-bench','docs') {
  $dir = "..\miniproj-$k"
  $t = Get-Content "$dir\plans\작업패키지\wp-$k.md" -Raw -Encoding UTF8
  $s = [regex]::Match($t, '(?s)## 상태\s*(.*?)\s*## 공통 규칙').Groups[1].Value.Trim()
  $changed = (git -C $dir status --short | Measure-Object).Count
  $commits = (git -C $dir log main..HEAD --oneline | Measure-Object).Count
  "[$k] $s"
  "      변경 파일 $changed개, main 이후 커밋 $commits개"
}
```

- 출력은 WP별 두 줄이다. 첫 줄은 세션이 적은 상태, 둘째 줄은 git이 센 변경 파일 수와 커밋 수다. 상태 줄의 갱신 시각이 오래됐는데 변경 파일 수가 늘고 있으면 세션이 상태를 적지 않은 것이다.
- 상태 줄은 세션의 자기 보고다. 완료로 적혀 있어도 완료 조건을 독립 기대값과 대조한 보고가 있어야 완료로 인정한다(AGENTS §7).

## 세션 모니터링 (2026-10-15 사용자 결정)

- **Claude 세션은 agent view(`claude agents`)로 본다.** 한 화면에서 세션별 상태(Needs input·Working·Completed·Failed)를 보고, Space로 출력을 훑어보며 답하고, Enter로 들어가고, Ctrl+X로 멈춘다. 터미널을 닫아도 세션은 계속 돈다. 연구 미리보기 기능이라 화면과 단축키가 바뀔 수 있다.
- 시작: 해당 WP의 worktree 폴더에서 `claude --bg "<시작 프롬프트>"`로 띄운다. 직접 만든 worktree 안에서 시작하면 agent view가 자동으로 만드는 `.claude/worktrees/` 격리를 건너뛰어(공식 문서 기준, 이 환경에서는 미확인) 정한 브랜치 이름이 유지된다.
- 셸 명령: `claude logs <id>`, `claude attach <id>`, `claude stop <id>`.
- **GPT 세션은 agent view에 나오지 않는다.** 별도 터미널에서 돌리고 위 "진행상황 한눈에 보기" 명령으로 확인한다.
- 두 도구의 역할이 다르다. agent view는 "돌고 있는가, 내 입력을 기다리는가"를, 집계 명령은 "WP 완료 조건 대비 어디까지 왔는가"를 본다. 둘을 같이 쓴다.
- agent teams와 tmux는 쓰지 않는다. 팀원을 worktree로 격리하지 않아 브랜치 분리와 맞지 않고, 실험 기능이며 토큰 사용량이 크다. 분할 화면은 Windows Terminal에서 지원되지 않는다.
- 주의: 세션 수만큼 사용량이 늘어난다(병렬 10개는 약 10배). 세션은 이 컴퓨터에서 돌아 컴퓨터가 꺼지면 멈춘다. agent view에서 세션을 삭제하면 Claude가 만든 worktree가 uncommitted 변경까지 지워지므로 삭제 전에 커밋한다(직접 만든 worktree가 영향받는지는 미확인).
- 시작 전에 `claude --version`을 확인하고 `claude agents`가 열리는지 본다(미검증).

## 완료 조건

- 각 WP가 에이전트 파일의 완료 조건을 독립 기대값과 대조해 보고한다. 일부만 확인했다면 확인한 범위와 못 한 범위를 구분한다.
- 병합 후 전체 테스트에서 새 실패가 없다.
- Databricks 원격 확인은 사용자 확인 전까지 '미검증'이다.

## 변경 (2026-10-15 10:10)

- WP-덤프는 보류한다. 위 표에서 WP-덤프를 기다리던 항목(대시보드 보강, 시간대·취소·주문 지표, 8-B·8-C·8-E·8-F)은 현행 덤프 기준으로 진행할 수 있다. 덤프 기대값 병합 후 재검증 단서는 현행 덤프가 바뀌지 않는 동안 적용하지 않는다.
- 증분 처리(계획 07의 7-B~7-F)와 증분 검증(7-D)은 필수 범위다. 신규로 들어오는 이벤트만 처리하는 방식으로 구현한다.
