# 계획 05. Metric View와 대시보드

## 목표

검증된 Gold 위에 지표 정의(Metric View) 2개를 만들고, 그 지표로 판매·환불 대시보드(2페이지)를 구성한다.

## 입력 / 산출물

- 입력
  - `commerce_poc.gold.{fact_sales_item, fact_refund, dim_channel, dim_product, dim_payment_method, dim_refund_profile}` (계획 04)
  - `01_contracts/contracts/event_spec.md` 6.5절(지표 정의), `01_contracts/data_fixtures/expected/expected.json`(독립 기대값)
- 산출물
  - Metric View `commerce_poc.serving.sales_metrics`(원천 `fact_sales_item`), `commerce_poc.serving.refund_metrics`(원천 `fact_refund`)
  - `03_serving/metric_views/` (한 파일은 한 가지 책임):
    - `metric_defs.py`: 두 정의(조인·분석 기준·지표 식)와 YAML·`CREATE OR REPLACE VIEW ... WITH METRICS` 문장 생성
    - `create_metric_views.py`: 스키마와 뷰 생성
    - `metric_check.py`: `MEASURE()` 조회 결과를 `expected.json`과 대조 (`gold_check.compare_metrics` 재사용)
    - `run_metric_views.py`: 실행 노트북 (호출만)
  - `03_serving/dashboards/`: `dashboard_spec.py`(데이터셋·위젯 정의), `build_dashboard.py`(Lakeview JSON 생성), `commerce_poc.lvdash.json`(생성 결과)
  - 테스트 `02_pipeline/tests/serving/`

## 설계

- **지표:** 정의는 event_spec 6.5절 그대로다. 판매 지표(총판매금액, 환불금액, 순판매금액, 환불금액비율, 상품결제건수, 상품결제단가, 결제고객수, 객단가)는 `sales_metrics`, 환불수량은 `refund_metrics`다. 환불 분석의 환불금액은 `fact_refund` 합이다.
- **분석 기준:** `sales_metrics`는 결제일·채널·상품·카테고리·결제수단, `refund_metrics`는 결제일·환불일·채널·상품·카테고리·환불 유형·사유다. 일자는 Fact의 `DATE` 컬럼이고 나머지는 Dimension 조인으로 얻는다. 일자 차원을 제외하면서(2026-10-14) 주·월·요일·공휴일 기준을 뺐다. 단 카드 5-G가 두 뷰에 **결제주**(`payment_week` = `date_sub(payment_date, weekday(payment_date))`, 월요일 시작)를 추가했다(2026-10-14 사용자 승인, event_spec 6.5절 반영).
- **비가산 지표:** 비율·단가·결제고객수·객단가는 식 안에 분자와 분모를 함께 넣어 조회 범위마다 다시 계산한다. 결제고객수는 `channel || '|' || user_id`의 distinct이며 `user_id`가 null이면 세지 않는다.
- **사유별 비중:** 구성비는 합이 1이 되는 값이라 지표가 아니라 대시보드 데이터셋에서 `환불금액 / SUM(환불금액) OVER ()`로 계산한다.
- **대시보드:** 판매 페이지(KPI 8개, 결제일별 판매·환불, 채널별 표, 결제수단별·카테고리별 총판매금액)와 환불 페이지(환불금액·환불수량, 사유별 표·막대, 결제일별·채널별 환불금액). 막대에는 비가산 지표를 쓰지 않는다.
- **필터(2026-10-13 추가, 2026-10-14 저장소 파일에서 제외; 아래 카드 5-F가 대체):** 필터 버전을 Databricks에서 열었더니 끊긴다는 사용자 보고가 있어, 저장소의 `commerce_poc.lvdash.json`은 필터 없는 첫 대시보드로 되돌렸다. 필터는 사용자가 Databricks에서 직접 붙인다. 생성기의 `build_dashboard(filters=True)`와 테스트는 남겨 두었다(제거 여부는 사용자 결정). 아래는 당시의 설계다. 기간(결제일, 날짜 범위)과 채널(다중 선택)을 전역 필터 페이지에 두어 모든 페이지 맨 위에 보이게 한다. 필터는 데이터셋 쿼리의 매개변수(`:date_range.min/.max`, `:channels`)로 Metric View 조회의 `WHERE`에 들어간다. 집계된 결과 행을 화면에서 다시 거르면 결제고객수·객단가·비율·구성비가 틀리기 때문이다. 환불 지표의 기간도 원결제일 기준이다(event_spec 6.3). 기본값은 기간 1년 전~오늘, 채널 전체이며 채널 선택지는 `dim_channel`을 읽는 데이터셋(`channel_options`)이다.
- **로컬 검증 방식:** 같은 정의의 조인·식을 일반 SQL로 풀어 sqlite에서 실행한다. `MEASURE()`와 YAML 해석은 Databricks만 한다.

## 카드 5-F. 상단 필터와 비교 기간 KPI (2026-10-14 추가)

참고 화면: `03_serving/reference/`의 스마트스토어 통계(카테고리 선택, 조회 기간, 자동 비교 기간, KPI 카드의 이전 기간·전년 비교). 이 카드는 위 "필터" 설계를 대체한다.

- **목표:** 대시보드 맨 위에 카테고리·조회 기간·비교 기간을 두고, KPI 카드마다 이전 기간 대비와 전년 동기 대비 증감을 보여준다.
- **필터 줄 (모든 페이지 맨 위):**
  - 카테고리: 다중 선택, 기본 전체. 선택지는 `dim_product`의 카테고리(현재 5개, 계층 없음). 전체 선택(`NULL`)을 쿼리가 올바르게 처리한다.
  - 조회 기간: 날짜 범위 선택기(결제일 기준). 1일/7일/30일 버튼은 만들지 않는다(2026-10-14 결정). 기본값은 상대 날짜 `now-30d/d` ~ `now/d`로, 시뮬레이터가 데이터를 계속 넣으면 실시간성이 반영된다.
  - 비교 기간: 읽기 전용 표시. 사용자가 입력하지 않는다.
- **비교 기간 계산 (쿼리 안에서 계산. Databricks는 파라미터를 다른 파라미터에서 계산해 만들 수 없다):**
  - 조회 기간 길이 `n = DATEDIFF(max, min) + 1`
  - 이전 기간 = `[min − n일, min − 1일]` (바로 앞의 같은 길이 구간)
  - 전년 동기 = `[min − 1년, max − 1년]` (윤일은 `ADD_MONTHS(…, −12)` 동작을 따른다)
  - 화면에 "비교 기간: YYYY-MM-DD ~ YYYY-MM-DD"를 같은 계산 결과로 보여준다.
- **KPI 카드:** 값, "이전 n일" 대비 증감률, "전년" 대비 증감률(▲/▼ 방향 표시). 증감률 = (현재 − 비교) / 비교. 비교 기간에 결제 건수가 0이면 증감률 대신 "실적이 없습니다."를 보여준다(참고 화면과 같다). 대상은 판매 KPI 8개와 환불 KPI 2개다.
- **비가산 지표:** 객단가, 결제고객수, 환불금액비율, 상품결제단가는 기간마다 Metric View에서 다시 계산한다(현재 기간과 비교 기간 값을 더하거나 나눠 만들지 않는다). 환불 지표의 기간도 원결제일 기준이다(event_spec 6.3).
- **나머지 위젯:** 차트·표는 같은 필터(카테고리, 조회 기간)를 따른다. 결제일별 추이에 비교 기간을 일차(1일째, 2일째…)로 맞춰 겹쳐 그리는 것은 선택 사항이다(필수 아님).
- **알려진 한계:** 조회 기간 끝이 오늘이면 오늘은 하루가 다 차지 않아 증감률이 낮게 나올 수 있다. 데이터가 2025-10-15부터라 전년 동기는 대부분 "실적이 없습니다."로 보인다.
- **작업 방식 (중요):** 사용자가 Databricks 화면에서 대시보드를 직접 구성한다(저장소 JSON 동기화는 연동되어 있지 않다). 산출물은 다음 순서로 준다.
  1. 데이터셋 SQL 전체(그대로 붙여 쓸 수 있는 형태, 로컬 테스트 통과)
  2. Databricks에서 위젯·필터를 구성하는 단계별 가이드 (`03_serving/dashboards/` 아래)
  3. 가능하면 가져오기용 JSON(`build_dashboard.py` 갱신)
  4. 사용자가 완성한 대시보드를 내보낸 JSON으로 `commerce_poc.lvdash.json`을 갱신하고, 그 JSON의 데이터셋 쿼리를 테스트가 대조한다.
- **입력 / 산출물:** `03_serving/dashboards/dashboard_spec.py`(필터·비교 데이터셋 정의), `build_dashboard.py`, 가이드 문서, `02_pipeline/tests/serving/`의 테스트
- **완료 조건:**
  - 로컬(sqlite 하네스): 소량 고정 입력과 손으로 계산한 독립 기대값으로 이전 기간·전년 동기·증감률이 맞다. 입력에 다음 경우를 넣는다: 기간 경계일, 결제고객수의 중복 제거가 기간마다 다른 경우, 비교 기간이 비어 있는 경우(실적 없음), 카테고리 선택 시 객단가 재계산, 환불의 원결제일 귀속.
  - 기존 데이터셋(필터 없는 버전)의 값이 깨지지 않는다.
  - Databricks(사용자 확인): 필터 줄이 맨 위에 보이고, 카테고리·기간을 바꾸면 KPI와 증감률이 바뀌며, 비교 기간 표시가 계산과 같다.
- **검증 방법:** `python -m unittest discover -s .\02_pipeline\tests\serving -v`, 그리고 사용자의 Databricks 화면 확인. 확인 전까지 '미검증'.
- **상태:** 5-G가 흡수해 구현했다(필터 줄·이전 기간·전년 동기·증감 문장·"실적이 없습니다."). 로컬 테스트 통과, Databricks 미검증.

## 카드 5-G. 대시보드 개편 (2026-10-14 와이어프레임 승인)

5-F의 필터·비교 기간 KPI 설계를 유지하고, 구성과 시각 규칙을 아래와 같이 개편한다. 사용자가 와이어프레임(판매·환불 2페이지)을 보고 승인했다. 그림 자체는 저장소 밖(Claude 캔버스)에 있으므로 이 카드의 글과 배치 스케치가 기준이다. 그림의 금액·곡선·막대 길이는 자리표시자다.

- **목표:** 멀티채널 대시보드가 채널 비교와 성장 추세를 한눈에 보이게 하고, 핵심 지표가 먼저 눈에 들어오게 한다.
- **5-F와의 관계:** 5-F의 필터 줄, 비교 기간 계산, KPI 증감(이전 기간·전년), "실적이 없습니다." 규칙은 그대로다. 아래 변경이 5-F를 확장하거나 대체한다.
- **변경 1. 채널 필터 추가:** 필터 줄은 채널(다중 선택, 기본 전체), 카테고리(다중 선택, 기본 전체), 조회 기간, 비교 기간(읽기 전용)이다. 모든 데이터셋이 같은 조건을 따른다. 5-F와 "범위 밖"의 "채널 필터 제외"를 이 카드로 대체한다.
- **변경 2. KPI 두 층:**
  - 판매 페이지: 큰 카드 3개(총판매금액이 가장 크다, 순판매금액, 환불금액비율), 작은 카드 5개(결제고객수, 객단가, 상품결제건수, 상품결제단가, 환불금액). 카드마다 이전 기간 대비 증감. 전년 동기는 큰 카드에만 보여주고 실적이 없으면 "실적이 없습니다."를 한 줄로 둔다.
  - 환불 페이지: 큰 카드 3개(환불금액, 환불수량, 환불금액비율). 환불금액비율은 `sales_metrics`의 `refund_ratio`를 같은 필터로 조회한다(원결제일 귀속이므로 값이 같다).
  - 증감은 방향 기호(▲▼)와 숫자로 쓰고, 초록·빨강 같은 상태 색으로 좋고 나쁨을 칠하지 않는다. 환불금액비율은 "낮을수록 좋은 지표입니다"를 작게 적는다.
- **변경 3. 추이는 선, 주별:**
  - "채널별 총판매금액 추이": 선 3개(채널별), 주별.
  - "환불금액비율 추이": 선 1개, 주별(주마다 그 주의 분자·분모로 다시 계산).
  - 환불 페이지 "결제일별 환불금액 추이"(원결제일 귀속): 선 1개, 주별.
  - 일별 막대(365개)는 쓰지 않는다. 주별을 쓰려면 아래 "명세 변경"의 분석 기준 추가가 필요하다.
  - 첫 주와 마지막 주는 조회 기간 경계 때문에 부분 주일 수 있다고 차트 아래에 표시한다. 환불 추이의 최근 주는 환불이 아직 접수 중이라 낮게 보일 수 있다고 표시한다.
- **변경 4. 분해 차트:**
  - 채널별 순판매금액 비중, 결제수단별 총판매금액, 카테고리별 총판매금액, 사유별 환불금액, 채널별 환불금액비율은 가로 막대이고 **큰 순서**로 정렬한다(동률이면 이름순으로 고정). 이름순 정렬은 쓰지 않는다.
  - 채널별 환불금액비율은 `sales_metrics`의 `refund_ratio`를 채널별로 조회한다. 금액이 아니라 비율로 비교해 채널 규모 차이가 가려지지 않게 한다.
  - 사유별은 막대 하나만 두고 금액·수량·비중은 아래 상세 표에서 본다(같은 값을 막대와 표로 반복하지 않는다).
  - 채널별 지표 표는 채널, 총판매금액, 순판매금액, 환불금액비율, 결제고객수, 객단가로 줄인다.
- **변경 5. 색 규칙:**

### 5-G 최종 시안 기준 구현 명세 (2026-10-14, 사용자 승인)

**기준 시안:** Claude Design 캔버스 https://claude.ai/artifact/CzuDV4PbqLs78GMWGNQKmE (판매·환불 2장, 비공개 링크). 이 절이 위의 와이어프레임 설명·배치 스케치보다 우선한다. 시안은 Lakeview로 그대로 옮길 수 있는 요소만 썼다: 6칸 격자, 위젯 하나에 값 하나, 위젯 종류는 counter·line·bar(가로)·table·text. 시안의 숫자·막대 길이는 자리표시자다.

**시안 요소와 Lakeview 대응**

- 페이지 머리(제목 "멀티채널 판매 현황", 판매·환불 탭): 대시보드 이름과 페이지 이름(`판매`, `환불`). 위젯을 만들지 않는다. 시안의 머리 부제(Metric View 이름 등)는 옮기지 않는다.
- 필터 줄: 전역 필터 페이지의 필터 3개(채널, 카테고리, 조회 기간). 기존 설계(카드 5-F·5-G 변경 1)와 같다.
- 섹션 제목(핵심 지표 · 추이 · 구성 · 상세): **text 위젯**(마크다운). 이번에 새로 추가하는 위젯 종류다.
- 숫자 카드: counter 위젯 하나. 카드 아래 회색 글은 위젯 설명(`description`). 숫자 서식(천 단위 쉼표, 원·명·건·개, 비율은 퍼센트 소수 1자리)은 화면 설정에서 지정한다(JSON의 서식 형식은 미확인).
- 증감: 페이지마다 비교 표 하나(`sales_compare`, `refund_compare`, 열: 지표 | 현재 | 직전 기간 대비 | 전년 동기 대비). 카드에 붙이지 않는다.
- 시안의 채널별 지표 표 안 채널 색 점은 Lakeview 표에서 낼 수 없어 뺀다.

**변경 (2026-10-14, 사용자 결정, 아래 표보다 우선):**

- **선택기를 페이지 안에:** 전역 필터 패널(Global filters 페이지)을 없애고, 각 페이지 맨 위(y 0, 높이 2)에 선택기 4개를 둔다: 채널(다중, x 0 폭 1), 카테고리(다중, x 1 폭 1), 조회 기간(날짜 범위, x 2 폭 2), 비교 기간(날짜 범위, x 4 폭 2). 선택기는 그 페이지 데이터셋에만 묶이고, 판매·환불 페이지는 각자 선택한다. 아래 두 배치표의 위젯은 모두 y가 2만큼 내려간다.
- **비교 기간 직접 선택:** 자동 계산(직전 같은 길이 · 전년 동기)을 없애고 매개변수 `compare_range`(날짜 범위, 기본 `now-61d/d` ~ `now-31d/d`)로 사용자가 고른다. 비교 표 열은 지표 | 조회 기간 | 비교 기간 | 증감이다. 카드 5-F의 "비교 기간 = 쿼리 안에서 계산, 읽기 전용"과 "이전 기간·전년 동기 두 열"은 이것으로 대체된다.
- **다중 선택 조건:** `channel_name IN (:channels)`는 Databricks에서 데이터셋 로딩 오류("Error loading dataset schema")를 냈다. `array_contains(:channels, channel_name)`로 바꾼 뒤 정상 동작을 사용자가 확인했다.
- 문구: 핵심 지표 섹션 설명은 "조회 기간과 비교 기간은 맨 위 선택기에서 고릅니다.", 비교 표 제목은 "조회 기간 · 비교 기간 대비". 시안도 같이 고쳤다.
