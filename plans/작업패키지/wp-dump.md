# WP-덤프: 덤프 모형 재설계

## 목표
요구사항(일 평균 약 5,000건 거래)에 맞는 규모로 1년 덤프를 다시 설계하고, 성장 추세와 급증 구간이 데이터에 뚜렷이 나타나게 한다.

## 배경
- 현재 덤프는 1년 합계 이벤트 약 567,735줄(카드 1-B: A 113,911 / B 278,137 / C 175,687), 하루 약 1,555 이벤트다. 목표는 하루 약 10,500 이벤트(주문 5,000 × 주문당 약 2.1건, 가정)로 약 6.8배다.
- 성장이 곡선에 잘 보이지 않는다. 계절 가중치(11월 1.25, 12월 1.2, 1·2월 0.9)가 연 25% 성장을 가린 것으로 추정되며 아직 확인하지 않았다.
- 이후 실시간 생성기가 이 로직을 재사용한다. 급증 구간 로직은 함수로 분리한다.

## 확정된 것 (2026-10-15 사용자 결정)
- SKU는 현행 15개를 유지한다. `sku_spec.md`, `skus.json`, `dim_product`는 건드리지 않는다. 슬라이드의 "상품 약 1,500개"는 이 PoC에서 충족하지 않는다.
- 변경은 `04_experiments` 안에서만 한다. contracts 변경이 필요해지면 멈추고 보고한다.
- 이미 정해진 것은 바꾸지 않는다: 고객 모델(채널당 30,000 시작 × 월별 수준), 월별 환불율 변동, KST 시간대 분포, 채널 차등 설정(A 20%·+30%, B 50%·+15%, C 30%·+40%), shock_correlation 0.8, Bronze 직접 적재(`eh_partition = -1`).

## 변경 내용
1. **성장:** 기간 시작 일 약 3,000건 → 끝 약 7,500건(약 2.5배). 연평균 (7,500−3,000)/ln2.5 ≈ 4,900건으로 일 평균 약 5,000건이다. 채널 성장 순서 C > A > B를 유지한다(예시 배수 C 3.5× / A 2.6× / B 1.8×, 합계가 평균 5,000이 되도록 보정). 계절 가중치 진폭을 줄인다(예: 11월 1.12, 12월 1.1, 1·2월 0.95).
2. **거래 단위:** 주문으로 가정한다(미확정). 확정되면 알린다.
3. **고객 수:** `customers_start`를 새 규모에 맞게 다시 정한다. 고객당 연 주문 수와 객단가가 현실적인지 점검한다(이전에 고객 수 결함으로 객단가가 약 1,115만 원까지 나온 적이 있다).
4. **급증 구간(가정값, 설정 파일에서 조정 가능):**

| 유형 | 모양(근거 있음) | 크기·빈도(가정) |
|---|---|---|
| S1 정시 행사 개시(푸시·플래시 세일) | 시작 시각에 급상승, 지수 감쇠, 종료 직전 작은 2차 급증 | 기저 대비 최대 5~10배, 상승 5분 이내, 감쇠 반감기 15~30분, 2차 급증 약 2배, 월 2~4회, 단일 채널 또는 전체 |
| S2 대형 행사일(11.11·11월 말·연말) | 하루 총량 증가 + 정오 사이트 전체 행사 개시 급증 + 20~22시 저녁 고원 | 일 총량 2~3배, 개시 급증 기저의 약 10배, 연 2~3회, 전 채널 |
| S3 다일 시즌 세일(선택, 사용자 확인 후) | 며칠에 걸친 고원 | 1.5~2배, 3일, 연 2회 |

- 근거: 정시 행사 시작과 끝의 급증은 ASOS 기술 블로그, 사이트 전체 행사의 정오 개시 급증과 저녁 피크는 Shopify BFCM 2025 자료, 행사일 총량 증가는 블랙프라이데이 주문량 평소 금요일 대비 +164%(풀필먼트 업체 기준)다. 배수와 감쇠 값 자체는 근거가 없는 가정이다.
- 급증 구간의 이벤트 시각은 초 단위로 생성한다.
- 급증 구간의 중복 전송률은 평소(1%)보다 높인다(가정 2~3%). 결제 실패(TIMEOUT) 비중 상승은 선택이다.
- 급증 이후 환불은 기존 지연 규칙(결제 후 1시간~10일)을 따른다.

## 입력 / 산출물
- 입력: `04_experiments/configs/dump.json`, `synth_scenarios.py`와 덤프 생성 코드, 현재 `results/expected_dump.json`
- 산출물: 새 설정과 생성 코드, `results/expected_dump.json`(독립 계산), 급증 구간 정의, 테스트

## 완료 조건
- 일 평균 주문이 약 5,000건(합계 약 182만 주문)이다.
- 계절 보정 후 월별 추세가 설정한 성장 배수와 맞는다(독립 계산으로 확인).
- 급증 창별 이벤트 종류별 건수와 최대 분당 건수가 `expected_dump.json`과 같다. 이 값은 생성기 코드와 로직을 공유하지 않는 별도 코드가 계산한다.
- 중복 제거 후 건수와 중복 전송 건수가 기대값과 같다.
- 생성 후 일별·종류별 실제 건수(취소·결제 실패·환불 비율)를 보고한다.

## 검증 방법
- 생성기 테스트와 `expected_dump.json` 대조. 규모·일수가 코드에 박힌 테스트를 먼저 목록으로 보고한다.
- Databricks 적재와 `check_*` 확장은 사용자가 실행한다. 그 전까지 '미검증'이다.

## 소유 경로
`04_experiments/` 전체(configs, src, results, 관련 테스트). `01_contracts/`와 `02_pipeline/`의 구현 코드는 수정하지 않는다.

## 공통 규칙 (모든 WP)

- 먼저 `AGENTS.md`, `plans/결정_로그.md`, `plans/09_병렬_작업_분배.md`를 읽는다. 충돌 시 우선순위는 최신 사용자 지시 > AGENTS.md > plans/ > 이 파일이다.
- **소유 경로 밖은 수정하지 않는다.** 밖의 변경이 필요하면 멈추고 보고한다. 다른 WP가 소유한 파일을 고치지 않는다.
- 변경안(파일, 기대값, 영향, 시간)을 먼저 제안하고 승인 전에는 수정하지 않는다.
- 독립 기대값(`expected*`, 픽스처)을 구현·테스트 통과를 위해 고치지 않는다. 테스트를 삭제·완화하지 않는다.
- 새 테스트는 코드를 일부러 망가뜨려 실패하는지까지 확인한다.
- 로컬 테스트 통과는 Databricks 성공이 아니다. 원격 확인 전에는 '미검증'으로 적는다.
- 전체 테스트에서 `regenerated_fixtures_are_identical`(채널 A·B·C) 3건은 이미 실패 중이다(CRLF 픽스처와 LF 재생성 비교). 이 WP의 변경으로 늘어난 실패와 구분해 보고하고, 이 3건은 고치지 않는다.
- 결정이 생기면 `plans/결정_로그.md` 맨 아래에 한 줄을 추가한다(기존 행은 고치지 않는다).
- UTF-8, 기존 CRLF 유지, BOM 없음. 비밀 값은 넣지 않는다.
- 작업 보고는 목표 / 입력·산출물 / 완료 조건 / 검증 방법 / 상태(완료·미검증·보류)로 쓴다. 확인한 범위와 못 한 범위를 구분한다.
- 작업이 한 단계 끝날 때마다 이 파일의 `## 상태` 절을 갱신한다. 형식은 한 줄이다: `상태: 진행중|완료|미검증|보류 / 갱신: YYYY-MM-DD HH:MM / 지금: <한 줄> / 다음: <한 줄> / 막힘: <없음|내용>`. 집계 명령이 이 절만 읽으므로 다른 내용을 섞지 않는다.
