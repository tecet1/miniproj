# 계획 08. Genie 에이전트

## 목표

Gold와 Metric View를 읽는 Genie 에이전트가 승인된 사용자에게만 응답하고, 그 답이 독립 기대값과 일치하는지 측정하고 개선한 과정을 설명할 수 있게 만든다.

## 배경과 결정

- 요구사항 2(자연어 분석 에이전트)의 구현이다. 목적은 "사용자의 질의를 Gold와 Metric View를 통해 신뢰할 수 있는 형태로 제공"하는 것이다.
- **왜 Metric View와 Genie인가:** LLM이 지표 정의를 그때그때 만들면 같은 질문에도 답이 달라진다. 객단가·결제고객수·환불 귀속 같은 정의를 Metric View에 한 번만 고정하고, Genie는 질문을 그 정의에 연결하게 한다. 접근은 Unity Catalog 권한으로 통제한다.
- **소스:** Gold 테이블과 Metric View 둘 다 읽게 한다(사용자 결정, 2026-10-14). Genie 한 에이전트에 테이블·뷰·Metric View를 합쳐 최대 50개를 붙일 수 있다(Databricks 문서).
- **제외한 것(2026-10-14 결정, `plans/결정_로그.md`):** 맞춤 에이전트 앱(Databricks Apps, 에이전트 SDK), Vector Search, Lakebase 대화 기록, 외부 판단 모델(Jev 등), 워크숍(`databricks/tmm`의 `agent_apps_workshop`) 코드의 이식. 이유: 요구(정확한 숫자와 접근 통제)를 Genie와 Unity Catalog가 이미 충족하고, 중간 계층은 틀릴 지점만 늘린다. 워크숍에서는 "결함 → 측정 → 수정 → 재측정" 반복 구조만 차용한다.
- **착수 조건:** 계획 06의 카드 1-D(덤프 적재 후 `check_*` 전부 OK)가 끝나야 한다. 72건 규모로는 답변 정확도를 평가할 수 없다. 이벤트 명세의 컬럼 이름이 바뀌었으므로 Metric View를 재생성하고 `check_metric_views`가 OK인 상태에서 시작한다. 계획 07(오케스트레이션과 품질 규칙)이 Silver·Gold 구현을 바꾸더라도 결과는 같은 독립 기대값과 일치해야 하므로 이 계획은 구현 방식에 의존하지 않는다. 다만 계획 07의 변경이 진행 중이면 Gold가 `check_*`를 통과한 시점에 시작한다. 이 계획은 컬럼 이름을 적지 않고 `03_serving/metric_views/metric_defs.py`의 현재 정의를 따른다.

## 범위

- 포함: Genie 구성 파일(소스 목록, 지침, 예제 SQL, 대표 질문), 질문 세트와 독립 기대값, 채점기, 접근 통제(그룹, 권한 부여, 공유), 측정·개선 기록, 설명 문서.
- 범위 밖(요청 전에 구현하지 않는다): 위 "제외한 것", 컬럼 마스크, 채널별 행 필터(카드 8-G, 사용자 승인 필요), Genie를 프로그램으로 호출하는 자동화(API 사용 가능 여부 미확인).

## 입력 / 산출물

- 입력: `commerce_poc.gold.*`, `commerce_poc.serving.{sales_metrics, refund_metrics}`, 지표 정의(`event_spec.md` 6.5절), 독립 기대값(`01_contracts/src/expected.py`와 `04_experiments/results/expected_dump.json`).
- 산출물 (`03_serving/genie/`, 한 파일은 한 가지 책임):
  - `config/`: `sources.md`(소스 목록), `instructions.md`(지침), `example_queries.sql`(예제 SQL), `common_questions.md`(대표 질문). 사용자가 Genie 화면에 적용하고, 적용한 내용의 기록이 이 파일이다.
  - `benchmark/questions.json`: 질문, 유형, 기대값, 정밀도
  - `benchmark/build_questions.py`: 기대값 계산(`expected.py`에서만, Gold·Metric View 조회 결과는 쓰지 않는다)
  - `benchmark/score_answers.py`: 답변 기록과 기대값 채점
  - `access.py`: 권한 부여 SQL 문장 생성, `run_genie_access.py`: 실행 노트북(호출만)
  - `runs/`: 측정 회차별 답변 기록과 채점 결과
  - `README.md`: 왜·어떻게·검증 설명(카드 8-F)
  - 테스트 `02_pipeline/tests/genie/`

## 작업 카드

작업 순서는 8-A, 8-D(로컬) → 8-B → 8-C → 8-E → 8-F다. 로컬에서 끝나는 카드는 Databricks와 무관하다.

### 카드 8-A. 질문 세트와 독립 기대값

- **목표:** 정확도를 판정할 질문 약 25개와 각 질문의 기대값을 만든다.
- **입력 / 산출물:** `expected.py`, `expected_dump.json`, 시나리오 → `benchmark/questions.json`, `benchmark/build_questions.py`
- **질문 유형(각 유형이 노리는 함정):**
  - 가산 지표(총판매금액·환불금액·상품결제건수) 4개: 기간·채널 조건
  - 비가산 지표(결제고객수·객단가·상품결제단가·환불금액비율) 5개: 일·채널별 값을 더하면 틀린다
  - 귀속 4개: 환불은 원결제일 기준, 날짜는 KST 기준 결제일
  - 기간 4개: 특정 월·구간 합계와 비교
  - 차원 분해 5개: 채널·카테고리·결제수단·환불 사유 비중
  - 지표에 없는 질문 3개: 방문수·전환율·취소율 등 명세에 없는 지표. 올바른 응답은 없다고 답하는 것이다(지표를 만들어 내면 실패)
  - 접근 통제 질문은 카드 8-C의 별도 시험이다
- **질문 작성 규칙:** 상대 날짜("최근 30일")를 쓰지 않고 절대 기간만 쓴다(데이터가 2025-10-15~2026-10-14로 고정이라 기대값이 변하지 않게). 한국어 질문이다. 각 질문에 `precision`(소수 자리, 건수·금액은 정수 일치)을 적는다.
- **완료 조건:** 모든 기대값이 `expected.py`에서 계산된다. 손으로 계산한 소수의 값(고정 픽스처로 확인 가능한 질문 포함)과 일치함을 테스트가 확인한다. 같은 설정이면 `questions.json`이 바이트까지 같다.
- **검증 방법:** `python -m unittest discover -s .\02_pipeline\tests\genie -v`. 계산 로직을 일부러 바꿔 테스트가 실패하는지 확인한다.
- **상태:** 미착수

### 카드 8-D. 채점기

- **목표:** 답변 기록을 기대값과 대조해 일치율과 질문별 결과를 만든다.
- **입력 / 산출물:** `benchmark/questions.json`, `runs/<회차>/answers.json` → `benchmark/score_answers.py`, `runs/<회차>/scores.json`
- **답변 기록 형식:** 질문 ID별로 Genie 답의 값, 생성된 SQL, 사람이 적은 불일치 원인(비어 있을 수 있음). Genie를 호출하는 자동화는 하지 않고 사용자가 화면에서 질문하고 기록한다(API 가능 여부 미확인).
- **채점 규칙:** 건수·금액은 정수 일치, 비율·단가는 질문의 `precision`으로 반올림해 일치. 허용 오차를 두지 않는다. 지표에 없는 질문은 사람이 "없다고 답함"을 판정해 기록한다. 지표 질문의 SQL에 `MEASURE(`가 있는지도 기록한다(지표를 Metric View로 계산했는지).
- **완료 조건:** 일치·불일치·판정 불가가 질문별로 나오고, 유형별 일치율이 계산된다. 입력 오류(없는 질문 ID, 값 형식 오류)는 조용히 넘기지 않고 오류로 보고한다.
- **검증 방법:** 로컬 단위 테스트. 채점 규칙을 일부러 망가뜨려(허용 오차 추가, 반올림 제거, 유형 누락) 테스트가 실패하는지 확인한다.
- **상태:** 미착수

### 카드 8-B. Genie 구성

- **목표:** 소스, 지침, 예제 SQL, 대표 질문을 저장소에 기록하고 사용자가 Genie 화면에 적용한다.
- **입력 / 산출물:** Metric View 정의 → `config/` 4개 파일. Genie 에이전트는 사용자가 화면에서 만든다.
- **지침에 담을 규칙(초안):** 지표는 Metric View의 `MEASURE()`로 계산한다. 비가산 지표(결제고객수·객단가·비율·단가)는 일·채널별 값을 더하지 않는다. 환불은 원결제일 귀속이다. 날짜는 KST 결제일이다. 명세에 없는 지표(방문수·전환율·취소율)는 만들지 않고 없다고 답한다. 소스는 Gold 테이블(상세 조회)과 Metric View(지표)다.
- **완료 조건:** 소스 목록이 Gold 6개 테이블과 Metric View 2개와 일치하고, 지침·예제 SQL·대표 질문의 내용이 저장소 파일과 화면의 설정이 같다(사용자 확인).
- **검증 방법:** 사용자가 화면 설정을 파일과 대조해 보고한다. 확인 전에는 '미검증'.
- **상태:** 미착수

### 카드 8-C. 접근 통제

- **목표:** 승인된 사용자만 Genie 응답을 받고 비승인 사용자는 받지 못함을 확인한다.
- **입력 / 산출물:** 승인 그룹 이름(사용자 결정) → `access.py`(필요한 권한 부여 SQL 문장 생성), `run_genie_access.py`(호출만). Genie 공유는 화면에서 승인 그룹에 CAN RUN으로 부여한다.
- **근거(Databricks 문서):** 사용자가 질문하려면 에이전트의 CAN RUN 이상과 사용하는 Unity Catalog 객체의 `SELECT`가 필요하다. 데이터 접근은 질문한 사용자 본인의 Unity Catalog 권한으로 판단하고, 권한이 없는 데이터를 물으면 빈 응답이 돌아온다. 웨어하우스 권한은 사용자에게 필요 없다(만든 사람의 자격 증명으로 실행).
- **완료 조건:** 승인 계정은 질문에 답을 받고, 비승인 계정은 응답을 받지 못하거나 데이터 접근이 거부된다. 두 계정의 결과와 사용한 권한 설정을 기록한다. 최소 권한(Gold와 `serving`의 `SELECT`와 필요한 `USE`)만 부여한다.
- **검증 방법:** 로컬은 문장 생성 테스트(어떤 객체에 무엇을 부여하는지, 누락·과다 부여). 실제 응답 여부는 사용자가 두 계정으로 시험한다. 비승인 시험 계정이 필요하다(준비 여부 미정).
- **상태:** 미착수. 시험 결과 확인 전까지 '미검증'.

### 카드 8-E. 측정과 개선

- **목표:** 기준선 일치율을 재고, 불일치 원인을 분류하고, 고친 뒤 다시 재서 개선을 숫자로 남긴다.
- **입력 / 산출물:** 카드 8-A·8-B·8-D → `runs/baseline/`, `runs/fix1/`... 각 회차의 답변 기록과 점수, 변경 목록
- **절차:** (1) 질문 전부를 Genie에 입력해 답과 SQL을 기록한다(사용자). (2) 채점한다. (3) 불일치마다 원인을 분류한다(지표 정의 오류, 필터·기간 오류, 귀속 기준 오류, 소스 선택 오류, 없는 지표를 만들어 냄 등). (4) 지침·예제 SQL·Metric View 설명 중 무엇을 바꿀지 정해 반영한다. (5) 같은 질문으로 다시 측정한다. Metric View 정의나 설명을 바꾸면 `check_metric_views`를 다시 실행해 OK여야 한다.
- **완료 조건:** 기준선과 개선 후의 유형별 일치율, 불일치 원인 분류, 변경 목록이 기록된다. 목표 일치율은 기준선을 측정한 뒤 사용자와 정한다(지금은 정하지 않는다). 기대값은 개선을 위해 수정하지 않는다(AGENTS.md §4). 기대값이 틀렸다고 판단되면 근거와 함께 보고한다.
- **검증 방법:** 채점기 결과와 사용자가 화면에서 확인한 답변. 확인 전에는 '미검증'.
- **상태:** 미착수

### 카드 8-F. 설명 문서

- **목표:** 왜·어떻게·어떻게 검증했는지를 한 문서로 설명한다.
- **산출물:** `03_serving/genie/README.md`: 구성도(Gold, Metric View, Genie, Unity Catalog), 이 구조를 쓴 이유, 앱 계층을 쓰지 않은 이유, 질문 세트와 채점 방식, 기준선·개선 수치, 접근 통제 시험 결과, 한계(미검증 항목 포함).
- **완료 조건:** 문서의 모든 수치가 `runs/`의 기록과 일치한다. 확인하지 못한 항목은 '미검증'으로 적는다.
- **상태:** 카드 8-E 이후

### 카드 8-G. 채널별 행 필터 (선택, 승인 전 구현 금지)

- **목표:** 같은 질문에 사용자 그룹마다 다른 답이 나오는 것을 보여 준다(예: 채널 담당 그룹은 자기 채널만).
- **상태:** **현재 범위 밖.** 하려면 먼저 '범위 이탈 경고'와 사용자 승인이 필요하다. Unity Catalog 행 필터가 Metric View를 거쳐서도 적용되는지는 확인하지 못했다.

## 완료 조건

- 질문 세트의 기대값이 모두 `expected.py`에서 나오고 로컬 테스트가 통과한다(8-A, 8-D).
- 승인 계정은 응답을 받고 비승인 계정은 받지 못한다(8-C, 사용자 시험).
- 기준선과 개선 후 일치율, 불일치 원인, 변경 목록이 기록되어 있다(8-E).
- 설명 문서의 수치가 기록과 일치한다(8-F).

## 검증 방법

- 로컬: `python -m unittest discover -s .\02_pipeline\tests\genie -v`
- Databricks: 사용자가 Genie 화면에서 질문하고 답과 SQL을 기록하며 두 계정으로 접근을 시험한다. 확인 전까지 '미검증'.

## 미확인 사항 (구현 전 사용자 확인 또는 문서 확인 필요)

- Metric View를 Genie 소스로 붙였을 때 `MEASURE()`로 올바르게 계산하는지(문서상 소스로 추가는 가능, 정확도는 8-E에서 측정).
- Metric View에 대한 `SELECT` 권한만으로 응답이 되는지(8-C에서 확인).
- Genie를 프로그램으로 호출해 답과 SQL을 받는 방법과 인증 방식(자동 채점이 필요하면 별도 승인).
- 한국어 질문에서의 품질(8-E 기준선으로 확인).
- 승인 그룹 이름과 비승인 시험 계정(사용자 결정 필요).

참고: [Genie 에이전트 설정](https://docs.databricks.com/aws/genie/set-up)
