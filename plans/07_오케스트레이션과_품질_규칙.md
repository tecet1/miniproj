# 계획 07. 상시 스트리밍 오케스트레이션과 선언형 품질 규칙

## 목표

수집은 상시, Bronze → Silver → Gold는 마이크로배치 상시 스트림으로 이어 돌리고, 품질 규칙을 사용자가 한 줄로 추가할 수 있는 선언형 목록으로 정의해 Spark에서 처리한다. 검증은 전수 조사가 아니라 증분으로 한다.

## 이미 정해진 것 (2026-10-14 사용자 승인)

- **검증은 두 층이다.** (1) 행 단위 규칙: PPT '데이터 품질 검증 시나리오'의 중복 제거, 누락 검증, 데이터 표준화, 컬럼 매핑과 이후 추가 규칙. 위반 행은 Quarantine으로, 정상 행은 Silver로 간다(현재 구현이 이미 충족). (2) 집합 단위 검사: PK 중복, 고아 행, 금액 정합성 등.
- **두 층 모두 선언형 규칙 목록으로 정의하고 Spark로 처리한다.** 사용자는 목록에 규칙을 한 줄 추가한다. 행 단위 규칙은 조건식과 위반 사유 코드, 집합 단위 규칙은 위반 건수를 돌려주는 SQL과 허용값을 갖는다.
- **Silver의 UDF 변환을 Spark 네이티브로 전환한다**(예정된 수순). 기존 픽스처 기대값(`expected.json`)과 1년 덤프 기대값(`expected_dump.json`)과의 결과가 바뀌지 않아야 한다.
- **전수 테스트와 멱등성 점검을 증분 방식으로 바꾼다.** 정답 대조(전수)는 가끔 도는 점검으로 남긴다.
- **상시 스트리밍으로 운영한다.** 수집(Function → Event Hubs)은 이미 상시다. Bronze 약 10초, Silver 약 30초, Gold 약 1분의 `processingTime` 트리거로 이어 돌린다. 숫자는 시작값이며 설정 파일에서 바꾼다. 예상 지연(최악 약 100초)은 계산값이고 관찰로 확인한다.
- **컴퓨트는 서버리스에서 All-purpose로 전환한다**(서버리스는 `processingTime` 미지원). 자동 종료를 끄고 상시 가동 비용을 허용한다.
- Gold는 Silver 변경분에서 이번에 바뀐 주문만 다시 계산해 MERGE한다. Metric View와 대시보드는 Gold 조회라 별도 실행이 필요 없다.
- Flink와 선언형 파이프라인(SDP)은 이번에 쓰지 않는다. SDP는 후속 비교 실험 후보다.

## 작업 카드

### 카드 7-A. 선언형 규칙 형식과 사용 방법

- **목표:** 행 단위·집합 단위 규칙을 한 줄로 추가하는 형식을 정한다.
- **입력 / 산출물:** 기존 Silver 검증 규칙(`validate_values.py`, 채널 변환의 필수 필드 규칙), `silver_check.py`·`gold_check.py`의 집합 검사 → 규칙 형식 설계 문서와 규칙 목록 파일(위치는 이 카드에서 정한다)
- **완료 조건:** 기존 규칙이 모두 새 형식으로 표현된다. 규칙 추가 방법(예시 한 줄 포함)이 문서로 있다.
- **상태:** 완료 (로컬, 2026-10-14). `02_pipeline/quality/`에 `rules.json`(행 규칙 9개, 집합 규칙 9개), `rules.py`(읽기·검사·SQL 만들기·판정), `README.md`(규칙 한 줄 추가 방법)를 만들었다. 테스트 25개(`tests/quality`)가 모양 검사·거부 조건·SQL 만들기·기존 값 검사 8개와 SKU 검사가 규칙으로 표현되었는지·README 예시가 유효한지를 확인하고, 변이 11가지가 모두 실패한다. 2026-10-14 로컬 Spark 4.2(`.venv`, JDK 21)를 갖춰 `tests/quality/test_rules_spark.py` 9개로 행 규칙을 기존 파이썬 검사와 차분 비교(150건 규모)하고 집합 규칙 SQL의 위반·증분 범위를 확인했다(변이 6가지 모두 실패). Databricks 실행은 미검증(카드 7-B·7-C). 채널 매핑표(PPT의 컬럼 매핑·표준화·누락 검증)의 선언형 형식은 카드 7-B에서 정한다.

### 카드 7-B. Silver를 Spark 네이티브로 전환

- **목표:** UDF(`convert_row`)를 Spark 표현식으로 바꾸고 행 단위 규칙을 선언형으로 적용한다.
- **입력 / 산출물:** 카드 7-A의 규칙 → `02_pipeline/silver/` 변환·검증 코드
- **완료 조건:** (2026-10-15 변경: `expected.json` 비교는 제거했다. 고정 픽스처 기대값 파일이 없으므로 변환 전후 Silver 결과가 같은지는 변환 전 코드의 출력과 직접 대조한다.) 덤프에서 `expected_dump.json`과 건수·분포·격리 건수·사유 코드가 이전과 같다. 로컬 테스트로 회귀를 확인하고 Databricks 실행은 사용자 확인 전까지 '미검증'.
- **상태:** 로컬 완료·Databricks 미검증 (2026-10-15). Silver 변환을 UDF 없이 Spark 표현식으로 바꿨다(`silver/native_convert.py`, 채널 매핑표 `channel_maps.py`). 로컬 Spark에서 격리 사유·event_id·공통 이벤트 전 필드·Silver 5개 테이블이 파이썬 기준 변환(`convert_row`)과 행 단위로 같음을 확인했다(시나리오, 오류 고비율 합성 데이터, 변형 51줄, 깨진 JSON). 한계: 숫자가 문자열로 오는 경우는 받아들인다(native_convert 머리말). Databricks(ANSI 모드) 실행은 미검증.

### 카드 7-C. 집합 단위 검사 이전과 결과 기록

- **목표:** 기존 `check_*`의 기대값이 필요 없는 항목(PK 중복, 고아, 키 누락, 금액 정합성, Bronze 균형)을 규칙 목록으로 옮기고 결과를 `commerce_poc.quality.results`에 쌓는다.
- **완료 조건:** 규칙이 위반하면 결과 행에 규칙 이름·단계·위반 건수가 남는다. 규칙을 일부러 어기게 한 데이터에서 위반을 잡는다.
- **상태:** 로컬 완료·Databricks 미검증 (2026-10-15). `check_silver`·`check_gold`의 정합성 검사를 모두 규칙(집합 규칙 21개)으로 옮기고 `check_layer`로 계층별 실행·기록한다. 일부러 두는 위반은 `report_by_design`·`report_exclusions`가 보고만 한다.

### 카드 7-D. 증분 검증

- **목표:** 전수 조사를 이번 배치 범위만 보는 검증으로 바꾼다.
- **완료 조건:** 마이크로배치마다 이번 Bronze offset 범위의 "들어온 수 = Silver 반영 + 중복 제거 + 격리"가 성립한다. 같은 배치를 한 번 더 처리해도 건수와 금액이 같다(증분 멱등성). 정답 대조(전수, `expected*.json`)는 별도 점검으로 유지한다. 기존 `check_*` 호출은 깨지지 않는다.
- **상태:** 로컬 완료·Databricks 미검증 (2026-10-15). 배치 균형과 금액 규칙(`silver_batch_amounts`)을 배치마다 기록하고, Gold 단계 증분 일관성(`gold_batch_consistency*`)을 추가했다. 같은 배치 재처리의 건수·금액 동일은 로컬 테스트로 확인했다.

### 카드 7-E. Gold 증분 재계산

- **목표:** Silver 변경분에서 바뀐 주문만 다시 계산해 Gold에 MERGE한다.
- **완료 조건:** 결과가 전체 재계산과 같다(1년 덤프 기대값과 일치). 이벤트가 순서와 무관하게 늦게 도착해도 같은 결과로 수렴한다.
- **상태:** 로컬 완료·Databricks 미검증 (2026-10-15). `gold/gold_incremental.py`: Silver CDF → 바뀐 주문·환불만 재계산 → 범위 MERGE. sqlite에서 무작위 도착·배치 분할 뒤 전체 재계산과 같음을 확인했다. CDF 읽기·범위 MERGE·스트림은 Databricks에서 확인해야 한다(1년 덤프 기대값 대조는 reconcile로 대체).

### 카드 7-F. 상시 스트리밍 전환과 Job 정의

- **목표:** 서버리스 → All-purpose 전환, 트리거를 설정 파일로 빼기, 스트림을 Job으로 묶어 재시작 가능하게 하기.
- **확인됨(사용자 보고, 2026-10-14):** All-purpose 컴퓨트에서 `run_bronze.py`가 문제없이 실행되었다. 서비스 자격 증명 방식으로 Event Hubs 인증이 된다. (접근 모드·런타임 버전은 기록 전)
- **검증 방법:** 먼저 All-purpose에서 Event Hubs 인증을 확인한다(위 확인 완료). 그 다음 Bronze → Silver → Gold가 이어서 도는지 사용자가 확인한다.
- **상태:** 로컬 완료·Databricks 미검증 (2026-10-15). 트리거 설정 `02_pipeline/pipeline_config.json`(bronze 10초/silver 30초/gold 60초) + `stream_config.py`, 상시 스트림 노트북 3개(`stream_bronze/silver/gold.py`), Job 정의 `jobs/pipeline_job.yml`(스트림 3태스크 무한 재시도 + 매일 reconcile)을 만들었다. 설정·노트북·Job 정합은 테스트로 확인했고, 클러스터 접근 모드·실제 배포와 상시 실행은 사용자 실행이 필요하다.

### 카드 7-G. 지연 관찰과 기록

- **목표:** 이벤트가 Event Hubs에 들어와서 Gold에 보이기까지의 시간을 측정해 기록한다(관찰값. 정량 목표는 세우지 않는다).
- **상태:** 도구 완료·측정 미실시 (2026-10-15). `quality/latency_probe.py`, `run_latency.py`. 테스트 주문을 보낸 직후 실행해 계층별 처음 보이는 시각을 관찰한다. 측정값은 사용자 실행 후 기록한다.

## 완료 조건 (전체)

- 규칙 목록에 규칙 한 줄을 추가하면 코드 변경 없이 적용되고 위반 시 Quarantine(행 단위) 또는 결과 테이블(집합 단위)에 기록된다.
- Silver UDF가 없고, 기존 픽스처·덤프 기대값과 결과가 같다.
- 상시 스트림이 돌면서 Gold가 기대값과 같다(재실행해도 건수·금액 동일).
- 검증이 증분으로 돌고, 전수 대조는 별도 점검으로 남는다.
