# 계획 06. 장기 데이터(1년치)와 랜덤 시점 적재 (04_experiments)

## 목표

1년치 합성 데이터를 덤프로 적재해 Gold·Metric View·대시보드가 장기 데이터에서 기대값대로 나오는지 확인하고, 이어서 시뮬레이터 서버가 채널별로 무작위 시점에 이벤트를 보내는 상황에서 파이프라인이 도착 순서·시점과 무관하게 같은 결과로 수렴하는지 확인한다.

## 이미 정해진 것 (2026-10-14 사용자 승인)

- **ID 규칙(확정):** 덤프와 운영(시뮬레이터)이 같은 규칙을 쓴다. ID는 불투명한 `STRING`이고 UUID 문자열(소문자, 36자)로 한다. 덤프는 이름 기반 UUID(v5, 시드 고정), 시뮬레이터는 무작위 UUID(v4)다. 명세는 `event_spec.md` 1.1절에 반영했다. 고정 픽스처는 읽기 쉬운 규칙 ID를 유지한다.

- 이 작업은 실험 단계(`04_experiments`)다. 정량 성능 목표는 세우지 않으며 처리 속도는 관찰값으로만 기록한다.
- 스키마 경로와 이름(`commerce_poc.{bronze,silver,gold,serving}`)은 유지한다. 필요하면 구조는 바꾼다.
- 1년치 데이터는 정해진 규칙(시드 고정)으로 만들어 덤프로 적재한다. 랜덤 적재는 시뮬레이터 서버를 두어 수행한다.
- 세 채널은 같은 내용을 갖는다(2026-10-12 결정). 채널별 값이 같게 나오는 것이 A/B/C 변환이 동등하다는 검증이 된다.
- 기존 픽스처(`01_contracts/data_fixtures`)와 그 독립 기대값은 바꾸지 않는다.

## 1단계: 덤프 (1년치)

### 입력 / 산출물

- 입력: `01_contracts/contracts/skus.json`, 기존 `scenarios.json`(픽스처 시나리오 포함)
- 산출물 (모두 `04_experiments/` 아래, 파일 한 개는 한 책임):
  - `src/synth_scenarios.py`: 시드 고정 난수로 `scenarios.json`과 같은 형식의 합성 시나리오를 만든다 (요일·월별 변동, 환불 유형·사유 5종 분산, 결제 실패 후 성공, 취소, 결제수단 5종, 자정 경계). 이벤트·주문 ID는 시나리오 ID에서 규칙대로 만든다.
  - `src/build_dump.py`: 픽스처 시나리오 + 합성 시나리오를 기존 `canonical`·`channel_a/b/c`·`generate` 모듈로 채널별 `events.jsonl`로 만들고, 같은 시나리오로 `expected.compute_expected`를 돌려 기대값 파일을 쓴다.
  - `src/send_dump.py`: `events.jsonl`을 읽어 `ingest.handle_event`로 봉투를 만들고(수신 함수와 같은 코드) Event Hubs에 배치로 보낸다. HTTP 구간만 건너뛴다.
  - `configs/`: 시드, 기간(2025-10-15 ~ 2026-10-14), 채널당 하루 주문 수
  - `results/`: 실행 설정, 생성 건수, 기대값, 확인 결과
  - 테스트 `02_pipeline/tests/experiments/`

### 설계 결정

1. **기대값의 독립성:** 합성 시나리오가 단일 출처다. 이벤트는 생성 모듈이, 기대값은 `expected.py`가 각각 시나리오에서 계산한다(둘은 로직을 공유하지 않는다). 기대값은 `results/`에 쓰며 `data_fixtures`는 건드리지 않는다.
2. **덤프 경로:** 로컬 스크립트가 `ingest.handle_event`로 봉투를 만들어 Event Hubs에 보낸다. Bronze의 `eh_partition`·`eh_offset`·`eh_enqueued_at`이 실제 값이라 Bronze 이후 경로는 그대로다. 이 덤프는 이 실험에 한정하며 일반 Backfill 기능이 아니다(범위 밖 유지).
3. **ID:** `ids.NamedIds(seed)`로 만든 UUID를 쓴다. 이름(시드·채널·시나리오·순번)에서 만들어 다시 생성해도 같은 ID가 나오므로 덤프를 다시 보내도 Silver 중복 제거가 같은 이벤트로 본다. 합성 시나리오 ID는 `L00001`처럼 픽스처와 달라 ID가 충돌하지 않는다. Silver·Gold의 ID 컬럼은 모두 `STRING`이라 컬럼 변경은 없다.
4. **재적재:** 기존 스키마를 지우고 픽스처와 합성 데이터를 한꺼번에 다시 채운다. 확인은 합쳐진 기대값 경로를 `check_*`에 넘겨서 한다.
5. **전송 전제:** 사용자 계정에 Event Hubs `Azure Event Hubs Data Sender` 역할과 `az login`이 필요하다(DefaultAzureCredential). 연결 문자열은 쓰지 않는다.

### 완료 조건

- 전송 건수 = 생성 건수 = Event Hubs 도착 건수 (`verify_arrival` 방식으로 확인).
- `check_bronze`, `check_silver`, `check_gold`, `check_metric_views`가 합쳐진 기대값에서 모두 OK: 건수, 금액, 채널별 값, 결제일별 분포, 격리 건수.
- 세 채널의 Gold 지표가 서로 같다.
- 같은 입력으로 Silver·Gold를 다시 실행해도 건수와 금액이 같다.
- 대시보드의 일자별 추세와 사유·결제수단 구성이 기대값 분포와 맞는다(눈으로 확인).

### 검증 방법

- 로컬: `python -m unittest discover -s .\02_pipeline\tests\experiments -v` (같은 시드로 두 번 만들면 같은 시나리오, 시나리오 검증 통과, 기대값이 독립 계산, ID 유일).
- Databricks: 덤프 적재 후 각 단계 노트북의 `check_*` 결과와 대시보드. 확인 전까지 '미검증'.

## 2단계: 시뮬레이터 서버와 랜덤 시점 적재 (초안, 1단계 후 확정)

- **서버:** 장기 실행 프로세스가 같은 합성 시나리오 모듈로 주문을 만들고, 채널마다 독립된 무작위 간격으로 기존 Function(HTTP)에 POST한다. 주문 안 이벤트 순서 뒤섞기, 소수 중복 재전송, 몰림과 공백을 옵션으로 둔다. 보낸 시나리오는 장부(append-only 파일)에 남겨 `expected.py`로 최종 기대값을 계산한다.
- **ID:** `ids.RandomIds`(UUID v4)를 쓴다. 명세 변경과 ID 생성 모듈은 2026-10-14에 반영했다(아래 상태 참고).
- **통과 기준:** 모두 도착하고 정리된 뒤 Gold가 기대값과 같다(도착 순서와 무관). 재실행해도 같다. PK 중복 0, Bronze 건수가 전송 건수와 같고 격리 건수가 주입한 오류 수와 같다. 중간 상태는 PK 중복과 참조 누락만 본다.
- **열린 결정:** 서버를 어디서 운영할지(Azure Container Apps, 함수 타이머, VM), 함수 키 보관(Key Vault는 범위 밖이라 환경 변수), 배포 방식(`.github/workflows`는 요청 시에만 건드린다).
