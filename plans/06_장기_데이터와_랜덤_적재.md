# 계획 06. 장기 데이터(1년치)와 랜덤 시점 적재 (04_experiments)

## 목표

1년치 합성 데이터를 덤프로 적재해 Gold·Metric View·대시보드가 장기 데이터에서 기대값대로 나오는지 확인하고, 이어서 시뮬레이터 서버가 채널별로 무작위 시점에 이벤트를 보내는 상황에서 파이프라인이 도착 순서·시점과 무관하게 같은 결과로 수렴하는지 확인한다.

## 이미 정해진 것 (2026-10-14 사용자 승인)

- **ID 규칙(확정):** 덤프와 운영(시뮬레이터)이 같은 규칙을 쓴다. ID는 불투명한 `STRING`이고 UUID 문자열(소문자, 36자)로 한다. 덤프는 이름 기반 UUID(v5, 시드 고정), 시뮬레이터는 무작위 UUID(v4)다. 명세는 `event_spec.md` 1.1절에 반영했다. 고정 픽스처는 읽기 쉬운 규칙 ID를 유지한다.

- **덤프는 Bronze 테이블에 직접 적재한다(2026-10-14 결정).** 덤프는 "이 기간 동안 이벤트가 정상 수집되었다"고 가정한 결과이므로 HTTP·Function·Event Hubs를 거치지 않는다. 그 구간은 픽스처로 이미 검증했다. Bronze 이후(Silver·Gold·Metric View·대시보드)는 그대로 검증한다.
- **`SINCE` 제거(2026-10-14, 구현 완료):** Bronze·Silver 실행과 `check_*`가 하드코딩된 시각으로 범위를 자르지 않는다. 읽은 위치는 체크포인트가 기억한다. 그 대신 검증은 Bronze가 이번 데이터만 담고 있다는 전제이므로 전체 재적재는 스키마를 지우고 다시 한다. (로컬 테스트 통과, Databricks 미검증)
- **시뮬레이터:** 서버 호스팅 방식은 어느 쪽이든 무방하다. 발표에서는 "서버"로 소개하고 구체 동작은 설명하지 않는다. 로직을 먼저 로컬에서 검증하고 호스팅은 그 뒤에 정한다.
- 이 작업은 실험 단계(`04_experiments`)다. 정량 성능 목표는 세우지 않으며 처리 속도는 관찰값으로만 기록한다.
- 스키마 경로와 이름(`commerce_poc.{bronze,silver,gold,serving}`)은 유지한다. 필요하면 구조는 바꾼다.
- 1년치 데이터는 정해진 규칙(시드 고정)으로 만들어 덤프로 적재한다. 랜덤 적재는 시뮬레이터 서버를 두어 수행한다.
- **성장 모형(2026-10-14 승인):** 월 수준 곱셈 경로(연 +25%, 월 변동 σ=2.5%) x 계절·요일·판촉 계수, 일 주문 수는 음이항분포. 시작 규모는 채널당 하루 주문 200건(연간 이벤트 3채널 합 약 56만 건). 근거와 가정은 `04_experiments/docs/기업_프로필과_성장_모형.md`.
- **Zerobus Ingest는 제외한다(2026-10-14).** 후속 비교 실험 후보로만 둔다.
- **`OTHER`는 이벤트에서 만들지 않는다.** 적재 단계가 결측·미정의 값을 `OTHER`로 바꾸는 값이다.
- 고정 픽스처는 세 채널이 같은 내용을 갖는다(2026-10-12 결정). 채널별 값이 같게 나오는 것이 A/B/C 변환이 동등하다는 검증이 된다. 1년치 덤프는 채널별 비중·성장이 다르다(2026-10-14 결정, `expected.py`의 채널별 시나리오 인자 확장).
- 기존 픽스처(`01_contracts/data_fixtures`)와 그 독립 기대값은 바꾸지 않는다.

## 1단계: 덤프 (1년치) — 작업 카드

공통 전제: 합성 데이터는 `04_experiments/configs/dump.json`의 시드와 모형으로 정해진다(성장 모형은 `04_experiments/docs/기업_프로필과_성장_모형.md`). 이벤트는 `NamedIds`(UUID v5)로 ID를 만든다. 합성 시나리오는 `OTHER`를 만들지 않는다(적재 단계가 변환하는 값이다). 대용량 중간 파일(채널당 이벤트 약 17만 줄)은 저장소에 커밋하지 않는다(`.gitignore` 또는 Volume).

### 카드 1-A. 합성 시나리오 생성기와 설정

- **목표:** 모형대로 1년치 합성 시나리오를 시드 고정으로 만든다.
- **입력 / 산출물:** `01_contracts/contracts/skus.json`, `configs/dump.json` → `04_experiments/src/synth_scenarios.py`, `02_pipeline/tests/experiments/test_synth_scenarios.py`
- **완료 조건:** 같은 설정이면 365일이 항상 같다. 모형 파라미터가 통계적으로 실현된다(월 로그 성장률, 음이항 분포의 평균·분산, 요일·판촉 계수가 월 규모를 바꾸지 않음). 연간 기대 주문 수가 보고서와 일치한다. 환불이 종료일을 넘지 않는다. 시나리오 검증을 통과한다.
- **검증 방법:** `python -m unittest discover -s .\02_pipeline\tests\experiments -v`. 코드를 일부러 망가뜨린 변이 13가지가 모두 테스트에서 실패함을 확인했다.
- **상태:** 완료 (로컬 38개 테스트 통과, 전체 433개). 이 표본(시드 20261014)은 채널당 주문 79,266건, 이벤트 176,343건이다.

### 카드 1-B. 덤프 생성과 합친 기대값

- **목표:** 합성 시나리오의 채널별 원본 이벤트와, 픽스처를 합친 독립 기대값을 만든다.
- **입력 / 산출물:** `synth_scenarios`, 기존 `canonical`·`channel_a/b/c`·`generate`·`ids.NamedIds`, 픽스처 시나리오(`scenarios.json`) → `04_experiments/src/build_dump.py`, `04_experiments/results/`의 합친 기대값 파일(작다, 커밋 대상). 채널별 이벤트 줄은 커밋하지 않는다.
- **완료 조건:** 기대값은 `expected.compute_expected(픽스처 시나리오 + 합성 시나리오, skus)` 한 번의 결과다(생성 모듈과 로직을 공유하지 않는다). 이벤트 줄 수(중복 전송 포함)가 기대값의 `bronze_rows`와 채널별로 일치한다. 같은 설정으로 다시 만들면 바이트까지 같다. 이벤트 ID가 채널 안에서 유일하다.
- **검증 방법:** 위 항목을 `02_pipeline/tests/experiments/`의 테스트로 확인한다.
- **상태:** 완료 (로컬, 채널별 비중·성장과 고객 수·시간대·환불율 변동 반영. 전체 464개 테스트 통과). 채널별 덤프 줄 수 A 113,911 / B 278,137 / C 175,687(합 567,735), 픽스처 24줄을 더한 기대 `bronze_rows` 113,935 / 278,161 / 175,711(합 567,807). 결제고객 A 17,215 / B 41,007 / C 26,160, 객단가 약 21.3만 원, 총 판매 약 180억 원, 환불 금액 비율 약 11.1%. 합친 기대값은 `04_experiments/results/expected_dump.json`(커밋 대상), 이벤트 줄은 `results/dump/`(`.gitignore`). 실행: `python .\04_experiments\src\build_dump.py`. 변이(고객 풀 고정, 환불 변동 0, 시간대 평탄·피크 이동, 채널 비중·성장 동일, 기대값이 채널 시나리오 무시, RandomIds, 기대값에서 픽스처 제외, 중복 전송 0)가 모두 테스트에서 실패함을 확인했다.

### 카드 1-C. Bronze 직접 적재

- **목표:** 생성한 이벤트를 합성 행 규칙대로 Bronze 테이블에 넣는다.
- **입력 / 산출물:** 카드 1-B의 이벤트 줄 → `04_experiments/src/load_dump.py`(Bronze 7컬럼 행 만들기와 insert-only MERGE), 노트북 `run_dump.py`(`load_dump`만 호출, 로직 없음). Databricks에서 실행한다.
- **합성 행 규칙:** `channel`, `payload`는 픽스처와 같은 형식. `received_at`은 이벤트의 `event_time`(UTC). `eh_partition = -1`. `eh_offset`은 A→B→C 채널, 줄 순서로 이어서 매긴 전역 일련번호(중복 전송 줄은 줄마다 다른 offset). `eh_enqueued_at = received_at`. `ingested_at`은 적재 시각. PK는 `(eh_partition, eh_offset)`.
- **완료 조건:** 로컬에서 행 만들기(컬럼, 타입, 규칙, 재생성 시 같은 PK)가 테스트로 확인된다. Databricks에서 같은 입력으로 재실행해도 행이 늘지 않는다(PK 중복 0).
- **검증 방법:** 로컬 단위 테스트 + 사용자가 Databricks에서 실행해 건수를 확인한다.
- **상태:** 미착수. Databricks 확인 전까지 '미검증'.

### 카드 1-D. 합친 기대값으로 단계별 확인

- **목표:** Bronze, Silver, Gold, Metric View가 합친 기대값과 일치함을 확인한다.
- **입력 / 산출물:** 카드 1-B의 기대값 파일 → `bronze_check.check_bronze`(픽스처 디렉터리만 기대값으로 삼으므로 합친 기대값을 받도록 확장), `check_silver`·`check_gold`·`check_metric_views`(기대값 경로 인자 확인). 기존 호출(픽스처만)이 깨지지 않아야 한다.
- **완료 조건:** 아래 "완료 조건"의 `check_*`가 모두 OK. 로컬에서 확장한 비교 함수가 테스트된다.
- **검증 방법:** 로컬 테스트 + 사용자가 전체 재적재(Bronze·Silver·Gold 스키마 삭제 → 픽스처 Function 경로 주입 → 덤프 적재 → 각 단계 노트북)를 실행해 `check_*`를 확인한다.
- **상태:** 미착수. 사용자 실행 필요.

### 카드 1-E. 결과 기록 (Cowork)

- **목표:** 실제 표본 결과를 보고서 8절에 기록한다 (월별 주문 수, 연간 이벤트 수, 매출, 시드와 설정).
- **상태:** 카드 1-B 이후. 현재 '미검증'.

### 설계 결정

1. **기대값의 독립성:** 합성 시나리오가 단일 출처다. 이벤트는 생성 모듈이, 기대값은 `expected.py`가 각각 시나리오에서 계산한다(둘은 로직을 공유하지 않는다). 기대값은 `results/`에 쓰며 `data_fixtures`는 건드리지 않는다.
2. **덤프 경로:** Bronze 테이블에 직접 적재한다. 이 덤프는 이 실험에 한정하며 일반 Backfill 기능이 아니다(범위 밖 유지).
3. **ID:** `ids.NamedIds(seed)`로 만든 UUID를 쓴다. 이름(시드·채널·시나리오·순번)에서 만들어 다시 생성해도 같은 ID가 나오므로 덤프를 다시 적재해도 Silver 중복 제거가 같은 이벤트로 본다. 합성 시나리오 ID는 `L20251015`처럼 픽스처와 달라 ID가 충돌하지 않는다. Silver·Gold의 ID 컬럼은 모두 `STRING`이라 컬럼 변경은 없다.
4. **재적재:** Bronze·Silver·Gold 스키마를 지우고 픽스처와 합성 데이터를 한꺼번에 다시 채운다(`SINCE`가 없으므로 Bronze가 이번 데이터만 담아야 한다). 픽스처는 기존 방식(Function 경로)으로 다시 주입한다.
5. **실행 위치:** 덤프 생성과 적재를 Databricks 안에서 한다. 로컬 `az login`과 Event Hubs Sender 역할이 필요 없다.

### 완료 조건

- Bronze 적재 건수 = 덤프 줄 수(중복 전송 포함) + 픽스처 72건, 같은 시드로 재실행해도 건수가 늘지 않는다 (PK 중복 0).
- `check_bronze`, `check_silver`, `check_gold`, `check_metric_views`가 합쳐진 기대값에서 모두 OK: 건수, 금액, 채널별 값, 결제일별 분포, 격리 건수.
- 픽스처 구간에서 세 채널의 Gold 지표가 서로 같다 (A/B/C 변환 동등성). 덤프는 채널별 규모와 성장이 다르므로 채널별 값은 채널별 기대값과 일치해야 한다 (2026-10-14 변경).
- 같은 입력으로 Silver·Gold를 다시 실행해도 건수와 금액이 같다.
- 대시보드의 일자별 추세와 사유·결제수단 구성이 기대값 분포와 맞는다(눈으로 확인).

### 검증 방법

- 로컬: `python -m unittest discover -s .\02_pipeline\tests\experiments -v`
- Databricks: 덤프 적재 후 각 단계 노트북의 `check_*` 결과와 대시보드. 확인 전까지 '미검증'.

## 2단계: 시뮬레이터 서버와 랜덤 시점 적재 (초안, 1단계 후 확정)

- **서버:** 장기 실행 프로세스가 같은 합성 시나리오 모듈로 주문을 만들고, 채널마다 독립된 무작위 간격으로 기존 Function(HTTP)에 POST한다. 주문 안 이벤트 순서 뒤섞기, 소수 중복 재전송, 몰림과 공백을 옵션으로 둔다. 보낸 시나리오는 장부(append-only 파일)에 남겨 `expected.py`로 최종 기대값을 계산한다.
- **ID:** `ids.RandomIds`(UUID v4)를 쓴다. 명세 변경과 ID 생성 모듈은 2026-10-14에 반영했다(아래 상태 참고).
- **통과 기준:** 모두 도착하고 정리된 뒤 Gold가 기대값과 같다(도착 순서와 무관). 재실행해도 같다. PK 중복 0, Bronze 건수가 전송 건수와 같고 격리 건수가 주입한 오류 수와 같다. 중간 상태는 PK 중복과 참조 누락만 본다.
- **열린 결정:** 호스팅은 1단계 뒤에 정한다(후보: 컨테이너, 함수 타이머, VM. Databricks 컴퓨트는 비용 대비 맞지 않아 제외). 함수 키는 환경 변수(Key Vault는 범위 밖), 배포는 `.github/workflows`를 요청 시에만 건드린다. 새 인프라가 필요해지면 범위 이탈 경고 후 승인을 받는다.
