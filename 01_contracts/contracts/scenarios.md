# 시나리오 명세 (소량 정답 대조 세트)

이벤트 생성기와 정답 대조 테스트가 따르는 기준 문서다. 기획안의 검증 시나리오(정상·중복·오류 이벤트를 주입해 Bronze → Silver → Gold 단계별 결과 확인)를 범위로 한다.

## 원칙

- 9개 시나리오를 채널 A·B·C에 **같은 내용**으로 적용한다. 채널별 차이는 원본 형식뿐이다(`channels` 명세 참고).
- 모든 ID와 시각은 고정한다. 생성기를 몇 번 실행해도 결과가 같다.
- 기대값은 파이프라인 코드와 로직을 공유하지 않는 계산 스크립트로 만든다. S01과 S09는 손으로 계산한 값과도 대조한다.
- 상품은 `sku_spec.md`의 SKU를 사용한다.
- 모든 이벤트는 자연스러운 순서(주문 → 결제 → 환불)로 송신한다. 중복(S19)만 같은 이벤트를 두 번 보낸다.

## ID와 시각 규칙

이 절의 ID 규칙은 고정 픽스처 한정이다. 장기·운영용 데이터의 ID 규칙(UUID)은 `event_spec.md` 1.1절을 따른다.

| 항목 | 규칙 | 예시 (채널 A, S01) |
|---|---|---|
| order_id | `{채널}-{시나리오}-{번호}` | `A-S01-1` |
| order_item_id | `{order_id}-{순번}` | `A-S01-1-1` |
| payment_id | `{order_id}-P{순번}` | `A-S01-1-P1` |
| refund_id | `{order_id}-R{순번}` | `A-S09-1-R1` |
| event_id | `{order_id}-E{순번}` (주문 안에서 발생 순서) | `A-S01-1-E1` |
| user_id | 시나리오 표 참고. 채널 안에서만 구분됨 | `U01` |

- 기준일은 2026-10-12(KST)다.
- 시각은 시나리오마다 시작 시각을 달리하고, 주문 → 결제는 30초 후, 환불은 결제 10분 후로 한다.
- 원본 시각 형식: A는 ISO 8601 UTC, B는 epoch 밀리초, C는 KST 문자열이다.

| 시나리오 | 주문 시각 (KST) |
|---|---|
| S01 | 10:00:00 |
| S02 | 10:10:00 |
| S04 | 10:20:00 |
| S06 | 10:30:00 |
| S08 | 10:40:00 |
| S09 | 10:50:00 |
| S19 | 11:00:00 |
| S21 | 11:10:00 |
| S23 | 2026-10-12 00:29:30 (= 2026-10-11T15:29:30Z) |

## 시나리오

### S01 정상 구매

- **목적:** 채널별 원본이 공통 모델을 거쳐 Fact 1행이 되는 기본 흐름
- **주문:** user `U01`, SKU-004 × 1 (89,000), 배송비 0
- **이벤트:** E1 주문 생성 → E2 결제 성공 (CARD, 89,000)
- **기대:** `fact_sales_item` 1행 (item_gross 89,000 · discount 0 · paid 89,000), 결제일 2026-10-12

### S02 배송비 부과와 경계

- **목적:** 배송비 규칙(2만 원 미만 4,000원, 2만 원 이상 무료)과 경계값
- **주문 ①:** user `U02`, SKU-013 × 1 (8,000), 배송비 4,000, 결제 EASY_PAY 12,000
- **주문 ②:** user `U02`, SKU-013 + SKU-014 (합 20,000, 경계), 배송비 0, 결제 CARD 20,000
- **이벤트:** 주문마다 주문 생성 → 결제 성공
- **기대:** `fact_sales_item` 3행 (①1행, ②2행). 결제금액 = 상품 결제금액 합 + 배송비가 두 주문 모두 성립

### S04 다중 상품·수량·할인

- **목적:** 상품 단위 할인과 결제금액 계산
- **주문:** user `U03`, SKU-001 × 2 (58,000, 할인 5,000) + SKU-010 × 1 (35,000, 할인 0), 배송비 0, 결제 CARD 88,000
- **이벤트:** 주문 생성 → 결제 성공
- **기대:** `fact_sales_item` 2행 (paid 53,000 / 35,000)

### S06 결제 실패 후 재시도 성공

- **목적:** 결제 실패 이벤트 처리, 주문당 결제 시도 N건
- **주문:** user `U04`, SKU-007 × 1 (59,000), 배송비 0
- **이벤트:** E1 주문 생성 → E2 결제 실패 (CARD, LIMIT_EXCEEDED, +20초) → E3 결제 성공 (EASY_PAY, 59,000, +50초)
- **기대:** `silver.payments` 2행(실패 1, 성공 1), `fact_sales_item` 1행 (성공 결제 기준, 결제수단 EASY_PAY)

### S08 결제 전 주문 취소

- **목적:** 주문 취소 이벤트 처리
- **주문:** user `U05`, SKU-014 × 1 (12,000), 배송비 4,000
- **이벤트:** E1 주문 생성 → E2 주문 취소 (CHANGE_OF_MIND)
- **기대:** `silver.order_cancellations` 1행, `fact_sales_item` 없음

### S09 수량 일부 환불

- **목적:** 환불 이벤트와 환불 합계 반영
- **주문:** user `U06`, SKU-010 × 2 (70,000), 배송비 0, 결제 CARD 70,000
- **이벤트:** E1 주문 생성 → E2 결제 성공 → E3 환불 성공 (수량 1, 35,000, RETURN, DEFECT, 결제 10분 후)
- **기대:** `fact_refund` 1행, `fact_sales_item` 1행 (refund_quantity 1 · refund_amount 35,000 · last_refund_date 2026-10-12)

### S19 중복 이벤트

- **목적:** `channel + event_id` 기준 중복 제거
- **주문:** user `U07`, SKU-001 × 1 (29,000), 배송비 0, 결제 BANK_TRANSFER 29,000
- **이벤트:** E1 주문 생성 → E2 결제 성공을 **같은 내용으로 2번 송신**
- **기대:** Bronze에는 2행 모두 보존, `silver.payments` 1행, `fact_sales_item` 1행

### S21 검증 실패 격리

- **목적:** 누락 검증과 오류 격리 (각 변형은 독립된 단일 이벤트, 주문 ID `S21-1`~`S21-3`)
- **변형 1 필수 누락:** 결제 성공 이벤트에서 `payment_amount` 없음 → `MISSING_REQUIRED`
- **변형 2 형식 오류:** 주문 생성 이벤트의 `quantity`가 숫자가 아닌 문자열 → `INVALID_TYPE`
- **변형 3 알 수 없는 이벤트:** 매핑표에 없는 이벤트 코드(배송 시작) → `UNKNOWN_EVENT_TYPE`
- **기대:** Quarantine 3행, Silver·Gold에 반영 없음

### S23 자정 경계 (UTC → KST)

- **목적:** 결제일을 KST 기준으로 계산하는지 확인
- **주문:** user `U01`, SKU-007 × 1 (59,000), 배송비 0, 결제 VIRTUAL_ACCOUNT 59,000
- **이벤트:** 주문 생성 2026-10-11T15:29:30Z → 결제 성공 2026-10-11T15:30:00Z (KST 2026-10-12 00:30:00)
- **기대:** `fact_sales_item` 1행, `payment_date` = **2026-10-12** (UTC 날짜인 10-11이면 오류)

## 보류한 시나리오 (미검증)

- 환불 변형: 같은 상품에 2회 환불, 상품별 다른 사유, 유형·사유 조합
- 도착 순서: 결제가 주문보다 먼저 도착, 환불이 결제보다 먼저 도착, 주문이 끝내 오지 않는 경우
- 이상 판정: 취소 + 결제 성공, 결제 성공 2건, 환불 수량·금액 초과, 같은 `event_id`에 내용 충돌
- 기타: 비로그인 주문, 참조에 없는 SKU, 결제 실패만 있는 주문
- 이상 주문 목록과 미결 목록(5분 기준)은 구현과 검증을 PoC 이후로 미룬다.
